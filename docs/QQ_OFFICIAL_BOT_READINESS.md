# 官方 QQ Bot：个人使用权限与应急切换准备

后续已根据用户要求实施实际并行试用，登录后台确认 AppID 并完成 WebSocket 接入；最新操作入口与验收边界见 [官方 QQ 试用](QQ_OFFICIAL_TRIAL.md)。下文为第一阶段公开资料调研记录。

核对日期：2026-11-10。已有机器人 [AppID 1903660238](https://q.qq.com/qqbot/dashboard/manage/1903660238)。已登录核验个人认证及 WebSocket 在线，并完成私聊日报与视频试用。尚未代用户提交外部申请。

## 结论与优先级

优先继续使用 NapCat，保留安装包、数据和可回滚配置；评估后续维护版本或可信兼容 Fork。官方 QQ Bot 可作为长期备用，但不是个人 QQ 号的无损替代。现阶段不能承诺只改一个开关就完整迁移：权限、OpenID 映射、消息历史和媒体差异必须提前解决。第一阶段实现见 [接入隔离与回滚](QQ_TRANSPORT_ADAPTERS.md)。

## 当前能力对照

| 现有能力 | 官方支持程度 | 落地条件/差异 |
|---|---|---|
| 人格对话、搜索、语境检索、图库词族、自动归类 | 后端可复用 | 模型与图库不依赖 NapCat；事件入口和发送格式另适配 |
| 群 @ 回复、文字与图片 | 有官方能力 | 应用消息权限、上线/服务范围、群添加与授权均需验收 |
| 普通群消息旁观、主动接话 | 有 `GROUP_MESSAGE_CREATE` 文档，应用权限待核实 | 文档要求开启“接收所有消息”；不能假设个人应用默认获得 |
| GIF、带文字表情包 | 附件/富媒体文档涉及 GIF | 能否按预期呈现为 QQ 表情、subtype 是否保留必须实测 |
| 视频与简介卡片 | 有视频/图片能力，需改发送策略 | 官方视频文档建议 30MB、硬限 200MB，当前 500MiB 上限不兼容；大文件需压缩或链接降级 |
| 引用回复 | 文档有引用参数 | OpenID、引用消息结构与窗口限制不同 |
| 合并聊天记录读取、任意历史回捞 | 未确认等价 API | 不能假设可补 NapCat 历史；仅利用已接收事件及自身留存 |
| 合并转发发送、跨群原生复用视频 | 未确认等价 API | 降级为逐张/逐段或单个媒体链接，控制次数与顺序 |
| 消息下挂 emoji 回应 | 群场景文档未支持等价能力 | 频道能力不能套用 QQ 群；必要时静默或文字反馈 |
| 定时学习日报、主动推送 | 文档有主动群消息 | 受应用授权、群范围及配额制约，不等同普通 QQ 无窗口发送 |
| 私聊、管理员管理、历史记忆 | 需官方身份适配与单独验收 | 原 QQ 号不可当 OpenID；昵称不能作为绑定依据 |

群消息文档当前列出个人机器人主动发送 60 次/分钟/机器人、20 次/分钟/群、1000 次/天/群；被动回复窗口 5 分钟、最多 5 条。以应用实际权限和后续平台更新为准。多段文字+图片可能消耗多次发送，适配器要合并回复并在预算不足时降级。

## 个人使用如何申请和确认

1. 登录已有应用管理页，核对个人实名/主体、开发状态、AppID、已开放接口与事件。公开首页说明个人可创建 5 个机器人、不提供公开服务、最多加入 500 群；这些是公开规则，不是此应用已获授权的证据。
2. 在“服务范围”检查允许服务的群与成员；“所有群聊/白名单群聊”和“设置权限”涉及群管理能力。公开前端列出的管理能力是撤回、进群管理、发言管理、移除成员、@全体，且说明实际使用仍需群主在群内单独授权。这里没有足够证据证明可申请全量消息接收。
3. 在“开发设置 → 事件订阅与回调地址”准备验签 Webhook 并订阅实际获授权事件。界面“全部接收”只指接收已订阅/获授权的事件种类，**不能据此判断拥有所有普通群消息权限**。
4. [官方 FAQ](https://bot.q.qq.com/wiki/bot_FAQ/)（2026-11-03 更新）明确：用最新版 iOS/Android QQ，以**群主身份**添加机器人时点“设置权限”，授权接收群内全部消息；主动在群内发言另行授权。这是手机 QQ 群内授权，不是网页事件订阅。既有机器人找不到入口时，应核对客户端版本及添加页权限设置，并用实际事件验证。
5. 分别检查应用权限与群管理员授权：错误 `11253` 表示应用缺少 privilege、需在平台申请；`11282` 表示群/管理员尚未授权。保存审批结果和实际事件样本，再做最小测试。

可提交给平台的询问正文（本次未发送）：

> AppID 1903660238，个人实名机器人，仅在本人管理且群主同意的群自用。希望使用 GROUP_MESSAGE_CREATE 接收普通群消息，用于语境回复与表情包检索。请确认个人主体是否可申请“接收所有消息”、准确菜单/工单入口、白名单与群主授权步骤，是否需要额外材料；并确认主动群消息、群图片/GIF/视频、私聊事件的申请条件与配额。若不可申请，请明确可用替代事件及限制。

不要在反馈正文放 AppSecret、访问令牌或 QQ 登录凭据。个人认证已核实；群内全量消息与主动推送的授权以群主设置及实际消息回执为准。

## 为快速切换提前准备的第二阶段

1. 取得上述权限，准备独立官方接入凭据和回调；验证鉴权、验签、去重、回复窗口、限流和事件重投。凭据放服务端配置，不进入仓库。
2. 实现官方事件/附件归一化，复用 Node 对话和图库；协议 ID 必须带平台/应用命名空间。建立经管理员确认的 `旧群号/QQ号 ↔ group_openid/member_openid` 映射，不按昵称自动合并。保留原数据，可撤销绑定。
3. 导入共享图库、语义索引和词族；按确认的身份映射接入群记忆、管理员权限和定时任务。未绑定身份不继承旧管理员权限或私人记忆。
4. 按能力对照表逐项验收；特别测试全量消息、GIF、大视频、引用、图片批量导入、定时报告和失败重投。没有历史 API 的缺口以已接收消息缓存补充，不能凭空恢复平台历史。
5. 准备预检命令：token、事件到达、群授权、身份映射、媒体可达、剩余配额和后端健康全通过才标记 ready。配置唯一活动入口，切换前暂停旧消费者和定时投递、记录在途未知消息，禁止自动补发。
6. 应急时选择已验收的官方入口并恢复任务，失败可回到 NapCat。对外清楚标注官方模式缺失的历史、原生转发及回应能力。只有完成前五步，才能把切换压缩为配置与服务操作；当前第一阶段尚不具备这一保证。
