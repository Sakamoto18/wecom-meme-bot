# 抖音作品类型与缓存隔离

2026-10-07：修复偶发的「先分享图文，再分享视频」类型错误。

- 旧实现根据异步轮播计数器、全页播放器和资源请求推断类型；页面加载顺序会改变结果，误判后的成功结果还会缓存 10 分钟。未发现不同短链的缓存键碰撞。
- 新实现读取页面初始数据（RENDER_DATA / Pace）或详情响应，只接受与目标作品 ID 一致的类型及资源。当前实测图文类型为 68，普通视频为 0；未知类型、资源缺失返回失败，不猜视频、不写成功缓存。
- 图文仅使用该作品的 images，每张图的 video 仍走原有 MP4 → GIF 转换；静态图、动图按原位置输出。普通视频只用该作品的 video 播放地址。
- 每次请求独立保存详情响应；解析结果携带 sourceId / contentKind。短链跳转造成的页面上下文销毁可在时限内重试。

验证：普通图文 5 张静态图；动态图文 2 张图、2 段动效；普通视频 1 条。覆盖两种分享顺序、冷/热缓存、错误作品 ID、数据晚到、未知类型、图文混合动效位置及失败重试。

发布：配套发布 Provider 和 QQ 解析器，重建 QQ 容器清除进程内旧解析缓存；不删除登录态。回滚必须同时回滚两者并清除解析缓存。图文 GIF 转换参数和失败时回退静态图的行为保持原样。

## 2026-11-27：详情超时与解析 CPU 优化

913546080 群截至北京时间 16:00 的 9 次抖音解析中有 3 次失败，均发生在作品详情获取阶段。原链接有效；复查发现桌面页有时返回验证码页面，页面加载也会令两核服务器满载。单独复测一个失败链接，Provider 进程组峰值占整机约 84%，29.56 秒后仍未取得详情。

原轮询另有两个问题：对详情响应任务使用 250ms 的 `asyncio.wait_for`，会取消尚未读完的响应体；每轮先等 DOM 数据，繁忙的渲染进程会阻塞已经收到的 API 详情。新增回归在原生产版的两种场景均失败，修复后通过。

现在先通过 HTTP 读取手机分享页的 `window._ROUTER_DATA` JSON，不执行网页脚本、不打开播放器；只接受目标作品 ID 一致且资源完整的数据。公开页读取最多 5 秒，数据不足时使用原持久化浏览器与登录态；部分图文手机页只返回外壳，仍需浏览器兜底。解析成功后释放 HTTP 响应，避免 Provider 长期保留响应体。

浏览器兜底优先处理独立捕获的详情，DOM 只保留一个进行中的读取任务，结束时统一清理；不加载图片、媒体与字体。最终媒体仍由原发送链路下载。作品 ID 校验、图文/视频判定、并发上限、35 秒总解析预算和跨群缓存保持原有约束。没有为官方 Bot 增加外部登录判断。

回归覆盖公开页无需渲染、错误作品 ID、非 JSON 脚本、HTTP 超时回退、静态/动态图文、慢详情响应、渲染无响应、跳转、并发及超时清理。

服务器同一视频短链对比：旧浏览器路径 29.56 秒失败，Provider 进程组采样峰值占整机 83.7%；新路径 1.30 秒成功，采样峰值 12.5%。这是一次定点对比，不能解释为全天 CPU 占用上限；图文浏览器兜底、视频转码及其他服务仍可能带来短时负载。

发布验证：26 项 Python 回归与 18 项 Node 回归通过；三条原失败链接均恢复解析。两条视频资源可读，图文三张图片用发送服务的 Node fetch 请求均返回 HTTP 200。Python aiohttp 诊断有一张返回 403，不能据此认定 Node 发送链路也失败。配置文件校验未变，NapCat 在线，官方 Bot 接收保持关闭。
